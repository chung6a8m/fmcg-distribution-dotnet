## Failure mechanism and frozen invariant

B.3 `LoginSession.Epoch`, `RevokedUtc` and B.4 `PreprodTenantRegistry.SecurityEpoch` are in Control Plane databases that may be PITR-restored. B.5 has a *separate* `B5TenantFence`, but B.3 logout/refresh-reuse/revoke-all and B.4 lifecycle transitions previously changed only their own rows. Rewinding those snapshots could restore old JWT/session or tenant authorization. At every protected effect, the **independently durable high-watermark** must be authoritative and fail closed when unavailable or inconsistent.

- **Monotonic session authority**: `B53SessionState(SessionId, ActorId, SessionEpoch, State)` in the independent B5 fence database. Registration is once-only; revoke increments once and cannot be undone by a B.3 snapshot. Same SessionId cannot be re-registered after restore.
- **Monotonic tenant authority**: existing independent `B5TenantFence` binding/registry/fence epochs, SUSPENDED/ACTIVE state. B.4 transitions advance the independent tenant row in the *same SQL transaction*; a restored older registry epoch cannot overtake it.
- **Non-bypassable operator path**: SQL DML triggers on the **versioned B.3 and B.4 tables** call narrowly scoped B53 stored procedures on the *same approved SQL Server instance*. Both source mutation and external authority update share one SQL Server transaction. If the independent database, SQL login/role, stored procedure or trigger is unavailable, the triggering mutation **ROLLS BACK**. Never substitute best-effort post-COMMIT queue or HTTP.
- **Independent activation**: a newly requested B.4 tenant bootstraps independent B5 state as SUSPENDED. Every registry step advances the epoch, and transition to ACTIVE additionally requires a single-use, five-minute, tenant/binding/target-epoch-specific permit from a separate B53 approver. Existing B.4 approved verification/finalizer conditions remain mandatory; the permit does not replace them.
- **Restore/current-bridge check**: `DurableRevocationGuard` asserts installed/ENABLED B.3 and B.4 bridge procedures/triggers *and* the independent current B53 session watermark before any protected SQL effect, on the same SERIALIZABLE connection and transaction. A restored B.3/B.4 snapshot from before the trigger/procedure was applied fails closed. B.5 original current session, registry, fence, role and membership checks remain mandatory.
- **No backfill by guessing**: if a physical B.3/B.4 registry already has sessions/tenants or the B5 authority already contains data, the B53 operator must establish an independently reviewed baseline or deny admission; do not mint ACTIVE rows or align epochs automatically. The source-only CI starts from an empty nonce-owned scratch environment.

## Runtime and trust boundary

- API group `/api/synthetic/app02/events` is mapped **only** when `SyntheticAuth:Enabled=true` and environment is Development/IntegrationTest. The DB connector enforces nonce-owned two physical LocalDBs, exact server-bound `tenant-a` / `tenant-b`, and signed tenant+actor+`producer_id` JWT. Request `ProducerId` must equal that signed producer identity (the synthetic fixture binds it to actor), not impersonate another producer; current-role grants and owner lookups use **BIN2 exact actor comparisons**, never SQL Server default case folding. No caller-provided DB, tenant, actor, producer authority, role grant, trusted cash witness or `verified` flag.
- `POST /intake` accepts versioned P/C **business fields only**. The authenticated actor, route tenant, event-v1 compact canonical bytes and SHA-256 are produced server-side. App-02 identity `(TenantId,ProducerId,EventId)` is independent of APP-01 commands; same key+hash replays a persisted outcome, changed hash 409 with zero new posting.
- P intake validates the **committed real APP-01D OFFER** source/command/Trip/amount/actor, then persists a nonposting P receipt. C intake can precede its exact named P: its receipt+progress commit first, then HTTP 202 durable intake ACK. Business APPLIED is a **different, later** SQL COMMIT; `GET /outcome?producerId=...&eventId=...` is owner scoped (UNKNOWN is an observer-only value). A lost HTTP response requires same-id retry/lookup, never a new ID.
- On intake, actor must possess JWT synthetic_role **and** an explicit, currently active `App02ActorRoleGrant` SQL row. Grant changes are audit-journaled; this is a synthetic test/operator ACL, **not production account administration or authorization**. Processing revalidates both initiating C cashier and named P sales SQL grants, trip, source, verified count and non-self actor.

## Worker, transaction and recovery

- `App02a3HostedWorker` is explicitly **opt-in** via `App02Worker:Enabled=true` in Dev/IntegrationTest with SyntheticAuth enabled, *never* in production. Internal worker has fixed synthetic tenant catalog, still enforced by LocalDB nonce and tenant marker. An in-process channel wakes the worker after a COMMIT; startup and every 15 minutes rescan durable SQL receipt/progress and outbox. The channel **is not** the source of truth.
- An independent Serializable transaction holds the same APP-01C/APP-01D per-trip application lock, resolves **the exact P event identity**, checks APP-01D committed offer and distinct verified cashier count, then calls the existing `App01dCashierUnloadService.AcceptAsync` inside the transaction. The APP-01 BusinessCommand/BusinessSource, exactly two ledger effects (`CUSTODY-OUT` and `FUND-IN`), APP-02 resolved edge/application/outbox/delivery and APPLIED transition **COMMIT or ROLLBACK together**. P never posts money; no new/shadow APP-02 ledger or second AR/receipt allocation.
- An absent, mismatched or opaque named P stays `PENDING_DEPENDENCY` without effect. A safety scan at 15m, expiration at **24h after durable C receipt** moves it to an owned `CASE` with `asOf`, reason and next action. No automatic late-P acceptance from CASE, deletion or assumed business REJECTED on missing ACK.
- SQL/transient technical failures roll back the in-flight apply, preserve earlier receipt and separately record at most **six** retries with exponential backoff (30s initial, 900s cap). Direct processor calls and event-driven scans must both honor the persisted `NextAttemptAtUtc` (including C receipts older than 24h); waiting for P / safety scans are **not** technical attempts. Six exhausted technical retries become CASE, not infinite silent reprocessing.
- CASE proposal requires a currently authorized cashier supervisor (Maker) different from initiating C. Independent checker with a different active role, distinct from Maker and C, approves `HOLD`, `CLOSE`, `APPROVED_RESUME`; both actions are separate authenticated API calls, with immutable proposal/disposition/approval linkage. An approved resume restores **the same event receipt/key** for full role/P/count/source revalidation. A prior CASE approval cannot reopen a new case.
- Post-APPLIED correction is a **separate nonposting audit annotation**, not a reversal of verified cash: `App02CorrectionProposal` records Maker's evidence, distinct active Checker commits a new `BusinessCommand` / immutable `CASH_HANDOVER_CORRECTION` source + zero-amount note line and `App02CorrectionLink` / immutable approval. The original APP-01D acceptance and its custody/fund effects remain unchanged. A correction source cannot post ledger effects under migration `202611170003`; an actual reversal or financial adjustment requires a future independent Owner-approved contract.
- Outbox dispatcher leases a stable MessageId (at-least-once), commits a distinct durable synthetic consumer inbox transaction, **then** writes sender ACK in a later transaction. Inbox dedups MessageId + version/hash; mismatched content fails closed. Lost ACK or worker restart leaves an observable lease that can be reclaimed after 2 minutes. Six failed delivery attempts become an observable delivery CASE; no real provider, invoice or accounting system is connected.

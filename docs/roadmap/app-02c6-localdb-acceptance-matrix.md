## 1. Fixture and run preparation

- Use the existing C.1–C.5 launchers and tests as references. Prepare a repeatable browser run and a separate read-only SQL comparison. Pin a clean reviewed checkout and required CI on that revision. PR #109 merge `34b24d8d09ef76f155e7b5f4e85c0f1d354ab191` is the starting reference. Record the actual tested revision and build hash in the run manifest.
- Use two new `Fmcg_App00_<nonce>_[AB]` databases with distinct tenant bindings. Before each target operation verify the LocalDB instance, exact database name, ownership marker, nonce and applicable binding. Bind web and API to loopback. Provision synthetic identities, current SQL grants and signing material outside Git. Use an operator-owned evidence directory.
- Proposed fixture values are synthetic unitless amounts, price 15, source unit cost 10, zero discount and zero tax, and a per-order cap of 1000. Use one SKU per scenario and isolate cases by source IDs and fresh or independently seeded fixture state. Start the standard flow in each tenant with MAIN 100 EA/value 1000 and TRIP zero. Run the canonical A flow in both tenants with distinct source IDs. Here A/B identifies tenants, while A_ONLINE identifies the sales channel in both.
- Proposed date fixture uses `Asia/Ho_Chi_Minh` as the seller timezone, using the existing DEV policy mapping to SQL Server `SE Asia Standard Time` and a controlled test clock. Use 2026-11-01 and 2026-11-08 as seller-local delivery dates, with 7-day frozen terms and 14-day successor terms. For the UTC boundary, propose Delivery instants 2026-10-31T17:05:00Z and 2026-11-07T17:05:00Z for the old order. Run the successor Delivery later on the same seller-local 08/11. Freeze exact policy effective instants and report cutoffs with the fixture. Carry the existing scoped 125% UI exception. [C.5 baseline and limits](../closeout/2026-11-22-app-02c5-dev.md)
- Freeze the fixture, expected SQL data and hashes before running. A controlled fault and clock must operate through the DEV harness against the actual API and DB path. Reuse the existing allocation source and command path for the report cutoff case. Resolve any missing harness capability before counting the affected case.

## D.1 proposed contract

### 1. Shared source model and compatibility

- **Recommended path for approval.** Extend the C.3 partial-batch approach and keep one set of `BusinessSource`, source lines, `StockRight`, `StockPool`, manifest, physical balance and ledger tables. Treat A and B as right kinds on explicitly validated source lines. `AReservation` supplies the A path and `BQuota` supplies the B path. Use a forward-only migration for the constraints and provenance fields needed by B.
- **Compatibility fence.** The current C.3 constraint permits only A on `IsC3=1` lines. Existing APP-01 B posting consumes legacy manifests (`IsC3=0`), and legacy unload fences out C.3 manifests. Keep these historical rows and existing behavior. Before D.1 review, show how the new B line is identified, how the A readers and writers preserve behavior, and how a single trip admits only its intended manifest model. Reuse the existing loading and source-posting logic where it preserves these invariants. A new B load cannot enter legacy posting or unload by clearing a discriminator or relaxing a generic role check. D.2/D.3 own their explicit posting/unload support for the new path. ### 2. B quota and credit

| Operation | Inputs and binding | Committed effect |
|---|---|---|
| **Grant B quota** | Command and source identity, prepared trip, warehouse and SKU, positive base quantity. Resolve current Warehouse authority and trip assignment on the server. Use the same stock pool as A, keyed by tenant, warehouse and SKU. | Reserve only free capacity `poolOnHand − poolAllocated`. In one transaction record the B right/quota, source and entitlement effect and increment the shared allocation. Physical quantity/value and AR/COGS/cash remain at their prior values. |
| **Grant B credit** | Command and source identity, prepared trip, active Customer, exact immutable ShipTo snapshot and positive amount. The proposed DEV issuer holds an explicit current Finance grant distinct from the checker. An authorized maker and a distinct checker bind version, scope, half-open effective interval and cap to the tenant/trip/Customer/B pool and synthetic unit. | Require exactly one effective approved decision. The pool cap cannot exceed that approval. Persist approval identity, source and capped grant with the pool counter in one transaction. An unused grant does not create AR, revenue, cash or stock effects. |
| **Load B** | Current Warehouse authority and assigned writer, prepared trip, right IDs, expected warehouse-held amounts and requested positive quantities. Use one warehouse for the batch. Bind each right to its original tenant/trip/warehouse/SKU and B quota. | Add the immutable manifest batch, source lines and paired physical custody effects. Decrease MAIN physical quantity/value and stock-pool on-hand/allocated by the loaded quantities, and increase TRIP physical quantity/value. Keep the delivery entitlement and credit grant available for later use. |

Use the existing matcher and bounded counter logic from the B quota/credit commands where compatible. For D.1 the DEV credit decision has an explicit scope and version and runs against a single server-side UTC instant. Missing, UNSET, pending, expired, future, ambiguous, self-approved or wrong-scope decisions deny a positive grant. Explicit approved zero means zero capacity. A positive grant also fails if the pool or the requested bound ShipTo disagrees with approved inputs. Freeze grant inputs and approval identity/version in the evidence. Before implementation, confirm Finance issuer, maker/checker duties and whether approval is Customer-scoped with a ShipTo-bound grant. The matrix assumes this model and retains the existing Customer pool cap across addresses. ### 3. Conservation and command behavior

- For an eligible D.1 right, `warehouse-held = granted − cumulative loaded` and `loaded remainder = cumulative loaded` before any later sale, release or unload. The full right is unchanged at load. For the shared pool, `0 ≤ allocated ≤ onHand` at every commit. Load decreases on-hand and allocated together, preserving available unallocated stock. Quantity and cost across MAIN/TRIP balance at each transfer, with the existing warehouse carrying-cost and rounding rules. AR, COGS, receipt, custody and fund are unchanged by quota, credit or load. [C.3 load contract](app-02c3-atomic-load-manifest.md)
- Keep current server tenant/actor/permission and trip assignments inside the protected command path. Use transaction-owned locking and deterministic lock order for competing pool/right/grant operations. A stale observed warehouse-held amount, over-capacity, wrong authority or invalid line rejects the whole batch. Partial loads are explicit commands against a right. An exception before commit rolls back all dependent writes.
- Use existing canonical command identity and source uniqueness. Same identity and payload returns the original durable outcome through a currently authorized path. A different payload conflicts. A new command ID with a reused source cannot duplicate an effect. Unauthorized replay is denied. Failed/denied operations preserve protected business fingerprints. A documented terminal rejection or security record may be added and must be identified separately.
- UI reuses the existing Sales workspace and shared controls. The D.1 screen exposes current quota, warehouse-held and on-vehicle quantities, grant proof/version, stale or forbidden outcomes, and same-command recovery. Server reports and SQL determine the displayed totals. No offline business write queue. The usual 125% scope exception applies. [Adopted UI baseline](../ui-ux/README.md)

# APP-02B.4 — Operator-owned PREPROD tenant provisioning runbook

**Not executed / not authorized for a physical environment by PR #58.** This runbook describes an operator change, **not** a deployment claim. Requires explicit DBA/Security approval for actual PREPROD host, approved primary Control Plane/SQL/Vault targets and independent reviewer; never run against production, LocalDB outside disposable tests, or any unowned tenant database.

## Prerequisites, reviewers and isolated principals

1. Record named DBA change approval, Requester / Approver / Provisioner / per-tenant Finalizer / Verifier / Security Suspension identities as distinct SQL Server logins, reviewed source commit SHA, migration file SHA-256, target privately routed SQL Server address, DB naming manifest, SQL access deny grants, Vault token ACL version, rollback/restore decision and immutable external audit-sink plan. **Do not seed or enable operator rows automatically**. Existing Identity control-plane migration `B3_20261117_001` remains subject to separate B.3/#52 operator approval.
2. Create or select the operator-owned **Control Plane** SQL database with independent DBA approval and secure TLS. Apply `src/FmcgDms.Preprod.Tenancy/Migrations/20261118_001_registry_control_plane.sql` using approved DBA identity on that target. It refuses system DB, existing partial schema and unknown version; replay with the exact version is idempotent. Require reviewed schema/permission fingerprints and separate backup of registry/audit; **never run via startup/Worker/HTTP**.
3. DBA creates explicit `PreprodTenantOperators` rows and least-privilege `EXECUTE` grants on required procedures, with distinct authenticated logins and no implicit tenant business data access. `CanRequest`, `CanApprove`, `CanProvision`, `CanFinalize`, `CanVerify`, `CanSuspend` are separately granted. Revoke direct `SELECT/INSERT/UPDATE/DELETE` on registry and event tables for operator logins; permit only role-approved stored-procedure EXECUTE, including guarded `cp_GetTenant` and verifier-only `cp_GetPeerForVerification`. The procedures use same-owner access and check `SUSER_SNAME()`, preventing post-commit snapshot reads from bypassing SQL least privilege. A DBA/system administrator cannot infer tenant business access. **No default operator**.
4. Five **separately ACL-scoped Vault KV-v2 role secrets**: `preprod/data/tenant-provisioning/{requester|approver|provisioner|verifier|security}` with each role's own limited `registryConnectionString`. **Only `provisioner` among shared role paths** may contain `masterConnectionString` (privileged DDL). A distinct one-tenant finalizer Vault token may read only `preprod/data/tenant-provisioning/finalizer/{TenantId:N}`, containing its matching `registryConnectionString` and restricted `masterConnectionString`; there is no shared `finalizer` path or wildcard grant. The verifier role alone can read its own approved tenant's `preprod/data/tenant-provisioning/probe/{tenantId:N}` with the scoped probe `connectionString`. These secrets/tokens **must be split by actual role**; the current offline CLI retrieves the operator data through its token and must only be run on an authorized isolated host with an appropriate ACL. Provisioning requires separate SQL DDL principal; verification probe principal must deny cross-tenant and Control Plane reads and *all* marker writes. Do not mount provisioning token on API/Worker. Control Plane SQL must use verified TLS, `TrustServerCertificate=False`.
5. Independently verify Caddy/API still health-only; `Runtime:ControlPlaneEnabled=false`, `Runtime:TenantRoutingEnabled=false`, `Admission=NO_GO`. No public tenant/provisioning endpoints, no tenant routes, no business mode. Physical Vault/port/RUNTIME-01/02 witnesses remain pending #54.

## Approved operator sequence (example syntax, not a live instruction to execute)

After a separate operator change authorizes a **nonproduction, privately scoped** target, set `DOTNET_ENVIRONMENT=Preprod` and `APP02B4_VAULT_ADDR=https://<approved-private-vault-host>` in the controlled operator runtime; mount a restricted file `/run/secrets/vault_tenant_provisioning_token`. Never supply SQL passwords, Vault token, database names or connection strings on the command line. Use `dotnet run --project src/FmcgDms.Preprod.TenantTool -- <action> <tenant-guid> [...]`.

| Action | Mandatory separate actor / input | Expected state |
|---|---|---|
| `request <TenantId> <lowercase-tenant-key> <ChangeRef>` | Requester (records only server-derived DB name) | REQUESTED |
| `approve <TenantId> <ApprovalRef> <ApprovedOwnerSqlLogin> <ProvisionerSqlLogin> <FinalizerSqlLogin> <RetirerSqlLogin>` | Separate Approver; approved non-secret SQL login names are bound immutably to this TenantId | APPROVED |
| `provision <TenantId>` | Non-sysadmin `CREATE ANY DATABASE` provisioner, leased; creates DB and marker | VERIFYING, still blocked (DDL login initially owns DB) |
| `finalize <TenantId>` | Dedicated per-tenant SQL finalizer; fenced owner transfer only | FINALIZING / NON_ROUTABLE; awaiting independent DBA retirement |
| `retire-finalizer <TenantId>` | **Different** DBA-authorized per-tenant SQL login + Vault token: disable old finalizer login, revoke owner IMPERSONATE, revoke tenant TAKE OWNERSHIP, drop DB user, kill active sessions and independently SQL-commit retirement | VERIFYING / NON_ROUTABLE only after exact binding/epoch/owner/retirement readback |
| `verify <TenantId>` | Separate verifier with probe secret and peer tenant physically present | Recorded witness, still VERIFYING |
| `activate <TenantId>` | Approver with current rowversion + verification witness and authority | ACTIVE in registry **only**, not API/Worker routing |
| `suspend <TenantId>` / `revoke <TenantId>` | Authorized security actor; epoch fenced in same Registry transaction | SUSPENDED/nonroutable |
| `start-reactivation <TenantId> <ApprovalRef>` | New authorization and re-verification, still SUSPENDED fence | REACTIVATION_VERIFYING/nonroutable |
| `verify <TenantId>` then `activate <TenantId>` | Distinct verifier/approver; final CAS denies concurrent revoke | ACTIVE if current gates |
| `abort-reactivation <TenantId>` | Verifier closes pending attempt | SUSPENDED |
| `decommission <TenantId> <ArchiveApprovalRef>` | Approved change and freeze | DECOMMISSIONING |
| `complete-decommission <TenantId> <ArchiveEvidenceRef>` | Independent verifier, protected records and archive | DECOMMISSIONED, **DB retained** |

The first tenant cannot receive B4 `verify` without a second independently registered/provisioned peer tenant, by design. If any check fails: stop, keep tenant nonroutable, preserve existing SQL and lineage, open an explicit remediation/CASE ticket. A database created but not marker-bound is quarantined; never assume a retry can adopt it automatically. Never use `DROP` as an implicit cleanup. An actual SQL DDL change and user grants require more owner-level signoff than this PR contains.

## Independent database-ownership handoff (mandatory; NOT executed in physical PREPROD)

- **Separate principals:** Approved per-tenant owner must be a distinct non-sysadmin/non-dbcreator SQL login without Control Plane operator or tenant business access except by explicit DBA policy. The provisioner has only `CREATE ANY DATABASE` (never `sysadmin`, `dbcreator`, `ALTER ANY DATABASE` or `CONTROL SERVER`). Provisioner applies the marker and grants `TAKE OWNERSHIP` *only on the exact newly created tenant database* to the SQL-approved per-tenant finalizer. A separate DBA-approved SQL server grant of `IMPERSONATE` on the explicitly approved new owner is required for that finalizer; no such authority is granted by the provisioner. A finalizer cannot use that role to create/drop a database or control another tenant.
- **SQL-authoritative approval:** Approver provides four *non-secret* login names named in the DBA/Security ticket with `approve`. `cp_ApproveTenant` freezes `ApprovedOwnerLogin`, `ApprovedProvisionerLogin`, `ApprovedFinalizerLogin` and `ApprovedRetirerLogin`. SQL `cp_ClaimFinalization` enforces `CanFinalize` only and refuses self/peer claims; it assigns a 5-minute fenced lease and a durable `FinalizationOperationId`. `cp_CompleteFinalization` requires matching current token, operation, binding, epoch and SQL `owner_sid`, and commits an immutable lifecycle event. Expired/stale completion and failure are denied; aborted/unknown ownership leaves the tenant non-routable. The SQL `cp_RecordVerification` and `cp_TenantTransition('ACTIVATE')` re-read `sys.databases.owner_sid` and the approved SIDs, independently of any CLI/Vault-supplied witness hash. A missing/changed owner or unapproved DDL principal is denied; no unconditional registry SELECT, API/Worker provisioning route, automatic adoption, or DROP.
- **Per-tenant scoped verifier Vault secret:** `preprod/data/tenant-provisioning/probe/{TenantId:N}` must contain `connectionString`, `approvedOwnerLogin`, and `provisionerLogin` matching the *separately approved* Control Plane binding. These names are not SQL passwords; the verifier must use a separate tenant read-only SQL principal that can SELECT the two marker tables, cannot UPDATE either, and cannot query peer or Control Plane business data. Treat missing metadata visibility as DENY, not evidence of isolation.
- **Independent operator witness:** Before calling `verify`, confirm exact database name/marker, SQL owner SID, distinct login SIDs and role/permission grants; with a session authenticated as the *actual provisioner login*, attempt denied direct SELECT/UPDATE on the tenant database; with the *actual scoped probe login*, assert own marker read, peer/control read deny, own marker write deny. Capture current `RowVer`, owner transfer SQL/provenance, before/after hashes, TestRunId, UTC, ticket, DBA operator and separate reviewer. SQL LocalDB CI uses SQL `EXECUTE AS LOGIN` to test the code path, **not** physical PREPROD attestation.
- **Boundary:** A SQL Server sysadmin can access the entire instance; an application-level Control Plane operator is **not** a sysadmin or a substitute for a physically independent privileged DBA. If the Owner requires data confidentiality even against instance sysadmin, stronger instance/key isolation is a separate design decision; do not claim B01-04 met by transfer alone. Actual grant, owner credential lifecycle and retention approvals remain PREPROD `NOT_VERIFIED`.

## Finalizer automation — CI-verified source, physical PREPROD NOT_VERIFIED

The `finalize` command reads a **per-tenant** Vault KV-v2 secret through the independently pinned HTTPS endpoint. It is never called by API/Worker and its SQL login must match the SQL-frozen `ApprovedFinalizerLogin`. The finalizer's only intended database DDL privilege is `TAKE OWNERSHIP` on that approved tenant DB; `IMPERSONATE` of the new approved owner must be granted by an independent DBA, not the provisioner. No `ALTER ANY DATABASE`, `CONTROL SERVER`, `dbcreator` or `sysadmin` login is permitted.

The SQL ledger separates provision/finalize/verify. `FINALIZING` always means non-routable. A failure or lease expiry can be retried only with a new fenced token and the **same durable finalization operation ID**; already-transferred ownership is recognized solely when `owner_sid` equals the SQL-approved owner. If the database has an unexpected owner, fail closed and open a manual CASE; never adopt it or DROP it. A concurrent `SUSPEND`/`REVOKE` invalidates finalization before COMMIT. SQL verification and activation independently require `FinalizedBy=ApprovedFinalizerLogin`, current binding, finalization evidence and owner SID. None of these controls route tenant business traffic.

**Updated #60 security handoff (source-only):** The independent `retire-finalizer` operator performs the previously missing revocation and SQL login retirement *before* calling `cp_CompleteFinalization`. SQL requires a separate approved `CanRetireFinalizer` actor, verifies finalizer login disabled, peer grants removed, no remaining active finalizer SQL session, and absence of the finalizer database principal; `cp_RecordVerification` and `ACTIVATE` also require that retirement lineage. A crash/lost ACK leaves `FINALIZING` and an independent DBA can retry the same durable operation without restoring privileges. **This is CI-source implementation only**: actual PREPROD privileges, operator IAM, technical Security/DBA approval and external immutable audit have not been exercised. Do not mark G-B01..05 or production admission PASS.

**Evidence class:** GitHub-hosted LocalDB verifies two physical disposable tenant DBs, distinct SQL impersonated principals, peer direct DDL denial, lease collision/takeover, stable operation ID, forged verification denial, and a revoked-inflight finalization. ### Independent DBA finalizer retirement responsibilities (2026-11-18)

Retirement is an operator-only second automation stage, not a request for the same finalizer to attest its own rights. Provisioner, Finalizer and Retirer must each receive distinct SQL logins and Vault tokens; the retire credential is **privileged DBA-owned**, never granted to API/Worker or mounted alongside finalizer. The per-tenant secret at `preprod/data/tenant-provisioning/retirer/{TenantId:N}` contains the DBA-controlled `registryConnectionString` and `masterConnectionString`, both server-certificate validated, and can only be read with a separately authorized token. The role policy template `deploy/preprod/vault-policy-b4-retirer.hcl` intentionally has no active grants until independently provisioned.

Required physical PREPROD steps: DBA/security approval of exact tenant/owner/provisioner/finalizer/retirer SQL login bindings; apply the **reviewed** migration with checksum; validate per-tenant `TAKE OWNERSHIP` and owner login `IMPERSONATE` delegation; invoke `finalize` then `retire-finalizer` as independent principals. Observe disabled finalizer in `sys.server_principals`, zero matching server IMPERSONATE grants, absence of the finalizer user in the tenant DB and no active sessions. Attempt an authenticated old-finalizer `ALTER AUTHORIZATION` post-retirement: must DENY. Inject interruption before and after revocation, stale lease/revocation, and peer/control owner-change requests. Record evidence/redacted source SHA, hashes, TestRunId, UTC, requested/actual/diff, DBA and independent Security reviewer. Failed cleanup or unavailable identity store leaves tenant `FINALIZING`/`SUSPENDED`, never ACTIVE. **No actual PREPROD execution is authorized by this PR alone.**
